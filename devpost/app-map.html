The learning loop (the kernel)

Every screen is one session.step. src/App.tsx renders the matching panel and is the only place steps change — always through go(), which asks canTransition() first so the loop can never skip the kernel.

How a child's answer becomes feedback (data flow)

  • NumberTiles → FractionAnswer.check() builds {n,d}.
  • detectAnswer(problem,{n,d}) → DetectionResult (correct / misconception / other / invalid) — a plain lookup, fully unit-tested.
  • App handler switches on the result: sets expression, speaks the matching lines.* line, and (for auto-transitions) waits for the line to finish before go().
  • Captions always mirror the spoken line, so the whole loop works with sound off.

Reuse these two patterns

  • Guarded state machine. Keep every screen in one enum, render with a switch, and route all transitions through a canTransition() table (machine.ts). It makes "impossible" navigation a compile-time/test-time error instead of a runtime bug. Reuse for any wizard, onboarding, or multi-step flow.
  • Deterministic validation without AI. Constrain the input (bounded tiles), then map it to a known category with a pure function + tests (detection.ts). Reuse whenever you'd otherwise reach for an LLM to judge a short, structured answer.

Run it

npm install → npm run dev (or npm run build && npm run preview). Tests: npm run test. Voice/SFX are pre-generated; regenerate with tools/gen_voice.py / tools/gen_sfx.py (needs the local .venv + Piper model, never shipped).
